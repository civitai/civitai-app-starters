`<civitai-chat>` recovers by itself from a reply the browser's network cut off. A browser drops every request in flight when the client's network changes (e.g. its address changes), which used to end the reply in an error the viewer had to answer with "continue". Such a reply is now asked for again, up to twice after a short wait (and, when the browser says it is offline, once it is back online, at most 15 s), resuming from the last step that finished: tools that already ran are not called again and words already kept are not repeated. Only fetch's own dropped-connection `TypeError` (`Failed to fetch`, `network error`) and a 2xx answer whose body such a drop cut (`Failed to process successful response`) count; a stop, any status the service sent, and every other error fail at once as before. A step that reports a tool call before it is cut is not asked again, so no tool can run twice. A reply that fails after its retries now says the connection was lost, and a step the stream closed after an error is no longer kept twice. Each retry fires `reply-retry` with `{ attempt, trace }` (type `ChatReplyRetry`) and is kept on the turn as `assistant.networkRetries` for the session; `reply-error` fires only once the retries are used up.
